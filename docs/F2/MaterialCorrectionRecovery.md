# 从逐项要求完成实际材料补正

本切片沿用原 §5.3、F2-T01/T02、AT23/AT35 的资料准备和独立核对合同。在 [实际诉求摘要](MaterialPreparationBrief.md) 之后，原获派专员可以要求企业为材料目录或诉求摘要提供新版；本切片把已存在的逐项要求连接到原输入框，并为普通材料命令补齐提交后精确事件核对。不发布政策条件，不生成新的接单报告。

## 原用户入口

1. 从全新 Case 开始，按原摘要流程明确选择事实、分享摘要，再提供自己的材料目录。原专员在同一事项勾选需新版的槽位并写明具体原因，执行原“要求补正”。
2. 企业可在冷页重新输入合法身份，从本人资料列表打开原事项。查看持久化的要求、原材料版本和原专员说明，点击“为此要求提供新版材料目录/诉求摘要”。按钮只选择槽位并定位原输入框；不填写正文或来源、不保存材料、不解决补正。已有人工候选或来源标签非空时拒绝覆盖，须由用户先提交或明确手动清空。
3. 企业提供实际新正文和有权使用的来源，以原“追加材料版本”提交。保存仅增加原材料版本/补正提交记录，仍是 UNVERIFIED；SUBMITTED_FOR_REVIEW 表示等待核对，不是已解决。
4. 原专员检查实际当前正文及来源，原 REVIEW 才能解决补正；企业再按原 CONFIRM 确认本地准备。Case 仍 NEEDS_INPUT，不推定资格、正式交付或外部受理。

## 中断与恢复的准确范围

普通原材料命令现在只有在 POST 后 GET 读回相同 revision/action/完整事件 payload，才能释放原 pending。网络失败、5xx 或无法核对精确事件都保持 UNKNOWN：保留原 key/body 和人工候选，隐藏旧材料、历史、补正、准备度投影，顶部显示当前状态待核对。禁刷新、重复新操作、来源写入、准备度、同事项资源关联与执行回执步骤创建；后两项除了禁按钮，还有 submit 的硬拦截。使用原请求按钮重试，不另生成 key。旧事件被核对只证明原操作已保存；页面随后显示当前资料，而不把历史事件称为当前独立审核。

原 key 只在当前文档内存中；没有将私密正文、token 或幂等 key 放入 localStorage。硬重载或切换身份后不会自动重放原写入。用户应以原身份打开原事项，检查当前材料及事件历史后决定下一步，不能把关闭页面当作“没有提交”。本轮冷页证据是在要求保存后及未知操作成功核对后读回持久资料；不证明硬重载时保留原 key。

已提交答复丢失的演练是实际服务器成功答复之后的客户端回读 503 注入，不是服务器持久化失败。两次原参数 POST 只追加一个目录 v2，冷页能读回原要求、新全文/来源和待审核状态；独立 API 检查实际文本、hash、原补正人工解决及 Case 状态。首轮流程完成后 driver 未保存报告，是重载清除其计数变量导致；已保留失败与清理记录，后续 driver 把原计数存于本地变量再复验。
