# ENG106 接单后的实际本地报告与新回执

ENG105 的准确终点是本人接单、人工填写 SYNTHETIC 回执、企业本地 ACK，再撤销访问。它没有调用接单后的业务适配器。原 worker 的正常 gateway 只执行建 Case 与事实评估；建单前的 LOCAL_CASE_CREATED 回执不能证明接单后办理。原设计产品 §5.5、§7.3 和阶段 F2-T04 要求实际本地记录、对应角色操作及效果/回执核验，原文没有规定此阶段另一项可直接复用的确定性办理动作。

本片新增一个明确有限的本地动作：`LOCAL_SYNTHETIC_HANDOFF_REPORT_CREATED`。获派执行者主动请求生成接单一致性报告；服务端代码核对当前 ACCEPTED offer、步骤、Case/Run、服务版本、父资料版本/hash 和当前精确租约，在原 PostgreSQL 事务中生成并保存结构化报告及新回执。输入不接受报告正文、adapter 身份或 verified 标记；不读取或输出材料正文。它是实际本地软件记录生成，不是模型执行、真实机构受理、线下履约或完整 PR0。

## 显式代码门

正常 `configured_app()` 不附加此适配器；已有访问桥接启用也不会自动启用办理。仅精确发行、实时匹配的原 `FixtureDatabaseEvidence` 自有全新临时数据库，另加 `--enable-isolated-local-execution` 才安装 nullable 回执 metadata 并在同一 API 进程附加适配器。原角色、Grant、生产 migration、原生 Windows 与 owner/ACL 不改。旧手工回执继续单独保留，不能因手填 source_label 冒充适配器产物。

正常环境的启用仍需原设计前提：明确当前授权主体与可审计的精确授权合同、明确服务动作及效果/核验合同、获授权的数据库安装与生命周期证明、最小应用写入能力及安全/原生验收。现有资料 REVIEW 不推出独立审批或生产安装权限；本片不代用户授予真实权限。原生创建 receipt 候选代码也不是本片 bridge 的合格临时库证明，不自动转为真实环境启用。

## 回执有效性与恢复

生成成果绑定精确接单、当前父来源、执行者、当前租约/权限摘要及唯一执行 ID。撤销、到期、权限版本改变、来源改变、责任方或接单代际改变时，旧成果保留为历史，但不能再满足当前企业 ACK 或 P4 核验。恢复 READ、重新批准、重开或要求纠正不复活旧成果；需要新明确办理请求、新成果和新的企业检查。相同 key/输入核对原提交，不能重新执行或移动指针复活历史。

报告与回执/原不可变事件在同一事务提交；发生异常或最后授权检查失败全部回滚。本动作没有外部非原子副作用，不借此宣称已解决任意连接的 OUTCOME_UNKNOWN。

实际结果见[机器证据](../integration/ENG106-LocalExecutionEvidence.json)：最终62项（新29+原33）通过、原消费端231通过、最终metadata101通过，分别保留冻结范围。最终全新单次浏览器从精确授权和接单到服务端报告/新回执/企业ACK，再撤销及原Run403完成；实际API读回唯一执行UUID/一版回执及CREATE/SUBMIT/ACK历史，30项三宽度检查通过。前3次失败、实际最后步骤与独立复核分别保留；不拼成全量或正式PR0验收。F1 未签收/F2 并行、R4 关闭、模型调用及预算 0，资格未知、外部受理未提交、线下履约无证据；原环境与备份保留。

启动这项有限动作需同时显式选择原访问桥接、全新夹具和新办理门：

```sh
PYTHONPATH=src:. python -m scripts.isolated_run_access_demo \
  --enable-isolated-run-access --fresh-fixture \
  --enable-isolated-local-execution --port 8765 --max-seconds 3600
```

执行者接单后使用“生成本地合成接单报告”；企业读取同一报告的执行 ID/hash 并另作本地核对。原手工 SUBMIT 仍是另一种记录方式；已经选择报告合同的步骤不能再降级为手工文字来通过当前检查。版本上限给新办理预留一次企业 ACK；没有容量时明确阻塞。

回显未知的实际 UI 负例只在服务端提交成功后替换客户端一次 GET 响应，并非服务端或模型故障。两次相同键/正文 POST 应返回同一执行 UUID，且只存在一次报告效果和一条生成事件；这与把两次请求误写为两次执行分开记录。
