# 普通人工回执冷恢复：刷新并发修复合同

基线为 `b3f64488cbcce8b29a8152509e3b2dac59d6aa84`，原协议及正式来源最小合同仍见 [ReceiptSubmitRecovery-20261018.md](ReceiptSubmitRecovery-20261018.md)。本片只修普通页面的人工 SUBMIT 恢复忙状态；不改后端、原键证明、批准、权限、模型或履约算法。

## 问题及用户结果

有效未知句柄冷页读取后，用户点击“只读核对原人工提交”，此 GET 未返回时点击“刷新当前回执”。旧实现递增 receiptGeneration，却保留 receiptSubmitBusy；旧 GET 的 finally 因不再属于当前代而不清 busy，于是新的核对和释放永久禁用。父级先指出静态可达路径，本片在未改生产源码上以真实 Chromium、普通 configured_app 子进程及自有合成 PostgreSQL 实际复现旧 200/403 两项失败。它是可用性卡死，未发现越权。

刷新后，用户现在可以在新上下文再次只读核对；旧请求迟到时不能结束新请求的忙状态、填入旧证明、清除原句柄或覆盖新草稿。

## 操作归属与保留的边界

每次 send/recover 取得独立的内存 operation 对象。loadReceipt 和 clearReceipts 在切换代时使旧对象失效，重置所选内存句柄、证明和 busy；localStorage 中原始坐标不删除、不改写、不自动过期清理。新详情读取成功后从同一原始存储重新选择当前句柄。

finally 只有仍持有同一 operation 对象才能结束 busy；更新按钮还须当前 generation/token/id 与原 raw 匹配。原每次 await 后的 current、句柄、TTL、原文精确比较守卫保持。刷新不绕过 entry 写入阻断；UNKNOWN 全局仍禁止新写入，只允许现有只读入口。HTTP 请求本身未取消；废弃的是旧结果的页面归属。

原存储替换、ABA、确定拒绝精确证明、当前撤权、草稿新编辑、历史与当前分开核对继续适用。释放仍需原 GET 证明、当前详情和原始存储再次匹配，绝不重 POST、ACK 或 P4。localStorage 比较删除仍不构成跨进程数据库级 CAS。

## 新回归的实际范围

4 个真实浏览器节点为旧响应 200/403 × 旧先返回/新核对先开始。全部先实际提交并丢失响应，再 reload 冷页，只通过普通控件发起 GET、刷新、重新核对和显式释放。检查新旧忙状态归属、证明、完整原句柄、同事项当前草稿、历史与权限快照、仅 GET、一次原 POST 及 320 视口。

403 使用已有另一企业 fixture-b 的 token 只替换被捕获旧 GET 的 Authorization，由实际后端产生拒绝后延迟交付给页面；这是明确的运输故障注入，不是撤销当前执行者权限，更不代表真实生产撤权场景。现有实际当前 READ 撤销测试保留。测试页面 request 事件不包括 route.fetch，不能当全网络 trace。

所有身份、目录、Run assignment、资料复核确认和原回执步骤来自普通启动前显式自有 SYNTHETIC fixture。它们不能用于普通批准、真实目录发布或真实任务授权。没有新增真实身份、Grant、分派、批准、凭据或模型调用。
