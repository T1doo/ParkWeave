## 本轮选择

最高优先级的**可在现有授权内直接实现**的业务切片是 V1 §5.1 明确要求的“既有材料在同企业、同用途授权下复用”，即 F2-T01 的实际缺口。正式发布与真实模型是完整链路的关键阻塞，但当前没有生产发布主体合同、真实赋权或模型预算；再做一轮发布 Mock 或再演示已有五步不能解决它们。

本轮只复用同一当前企业负责人拥有的、同园区/企业、同服务 ID 与版本、SYNTHETIC 资料事项的 `material_outline`。不复用旧诉求摘要、目标、审核、确认、身份、Grant、Run assignment 或办理结果。来源须是当前确认的完整快照、正文 SHA 与来源版本一致、没有待补正请求且材料不是递归复用副本。目标是该负责人新建、无材料和办理记录的独立 Case。

用户明确选择一份源材料目录、查看内容与版本，确认只用于同一服务的新 Case 并填写理由。服务端同时锁定和检查来源/目标当前授权、Case/Run/负责人绑定、来源 SHA/版本/审核快照、目标 revision。新建独立 evidence UUID / v1 / UNVERIFIED，保存原来源与精确旧版本的历史 provenance；同事务写原 ADD_EVIDENCE 事件并失效目标材料核对。schema 仍24，无新增 DDL、权限或赋权入口。

新 Case 必须提交自己的新诉求摘要，并由其原获派专员独立人工 REVIEW、负责人 CONFIRM。来源后来更新不会改写已复制的文本、编号或历史；来源当前状态与复制快照分开显示，历史复制不表示实时引用或事实核实。复用材料后仍不能自动资格判断、受理或关闭原业务目标。

这不是 T06/AT08 的新企业模板冷启动。源、目标是同一负责人明确授权的独立资料；跨企业、跨负责人、跨服务和跨用途共享拒绝。真实资料如需 item-level/purpose-level 授权，应另行定义并核验合同，当前仅合成范围不能推断此能力。

## 完整链路与后续优先级

完整链路应是：新诉求/事实与用途授权 → 正式版本服务目录及模板 → 保留全部目标的规划和预览 → 用户确认与当前 Approval → 新 Run 的合法访问准备 → 资源与责任方办理 → 独立业务回执 → 目标验收/反馈 → 新输入重新运行。现有合成步骤证明中间部分，不能把链路两端缺口藏在状态标签中。

本轮之后优先明确正式 ServiceRelease 的来源维护、作者、独立审核、发布/撤回主体和精确对象范围，并将其与单 Run 访问批准的生产合同分开。这些决定落实后才能把既有默认关闭候选接入正式目录与新 Case 入口；若未落实，保持阻塞，独立推进 AT06 的用途/冲突数据合同或 T05 的真实已授权本地动作恢复。真实模型 AT02/07/30 继续受 R4/预算与账号条件限制，不能用开发模型代替。

Windows 独立设计修复见 [ENG100-WindowsGenerationAuthority.md](ENG100-WindowsGenerationAuthority.md)：不再复测缺少 target file-ID CAS 的名称替换。原生安全动作仍暂停；低敏感合成协议文件可做普通隔离创建和只读验证，不改变 ACL、身份或攻击模型。

## 本轮实际验证

新路径为 `GET/POST /api/preparations/{preparation_id}/material-reuse`。GET 先显示来源目标/版本等元数据，只有明确选择材料才取正文；POST 使用来源/目标 revision、精确 evidence ID、版本、正文 SHA、审核快照 SHA 和原幂等键。来源与目标在同一事务按稳定顺序锁定，所有返回旧结果也先重验当前授权。来源不可访问时历史只显示目标自己的编号/摘要；目标获派审核者不能读取旧 Case 的 provenance。

材料专项最终 **32 PASS，0 FAIL/ERROR/SKIP，2 WARN，10.84 秒**；既有准备兼容 **68 PASS，19.40 秒**。首次专项的 10 项失败来自测试误用 POST 200（原实际合同为201）和未创建真实 version2 目录 fixture，已修正并保留日志；没有把路由未实现的404当产品行为基线。原 ADD_EVIDENCE 拒绝伪造 lineage 的基线单测实际1PASS保留。版本不同负例在真实新目录、原 REOPEN/REVIEW/CONFIRM 后验证，避免陈旧审核先阻断而遮住版本门禁。

最终实际浏览器 **1 PASS，39.45 秒，9 张1200/390/320宽截图**，两份独立新 Case/Run/准备在浏览器前经原 API/core 创建。开始后只有原网页操作，无业务数据库 setup 写入。实际完成来源双槽提交与人工核对/确认、显式用途复制、已提交答复丢失后的原 key/body 重试、目标自己的新诉求、来源新版提交、目标独立 REVIEW/CONFIRM、刷新与切 Case/token 私密响应隔离；共5份证据、12个准备事件，其中仅1次实际复用，11次POST包含同键重试。七张权限表 hash 不变，无 assignment、resource、model 新记录，服务停止。复制材料即使本地核对后 `authenticity` 仍 UNVERIFIED；原 Case 仍 NEEDS_INPUT，未验收目标或提交外部受理。
