# ENG097 V1 范围核对与材料补正切片

## 目的与状态

本记录对照原始《平台产品设计》§5.1–5.2、§5.5、§6.2–6.3，《分阶段开发计划》F2-T01/T04/T06/T07 与 `docs/验收规格.json`，选择一个不依赖正式服务目录发布权、也不改变身份或 Grant 的可实现增量：把专员提出的材料补正要求具体绑定到当前材料槽与版本，并在企业提交新版后由原获派专员重新核对。

这是范围和验收提案，不是已实现或已通过的产品能力。验收规格中的42项当前仍为 `NOT_RUN`；专项测试或一个已有合成 Case 的成功流程不能替代正式 AT 签收。

## ENG097 推荐行为合同

### 补正要求

- 只允许已有获派 `park_specialist` 在其当前 `REVIEW_ASSIGNED` scope 内，使用现有 `REQUEST_CHANGES` 合同提交原因，并可明确选择 `need_summary`、`material_outline` 中一个或两个槽。保持企业 `PREPARE`、专员 `REVIEW_ASSIGNED`、当前 `READ`/tenant/Case 检查；不增加角色、权限或 Run assignment。
- 每个被请求的槽都记录稳定 request UUID、请求者、理由、Case/preparation、请求时 preparation revision，以及该槽当时的 evidence version/ID/source hash；若当时缺材料，明确记录 base 为“缺失”，不可猜成版本1。
- 同一槽再次被要求补正时，只将该槽的前一个未解决请求标为 superseded，并保留原请求和原因历史。其他槽未解决请求必须继续保持未解决；一次新请求不能清掉其他槽的待办。已经解决的旧请求保留为历史，后续新请求产生新的请求记录。
- 旧客户端不传槽位时保持现有 API 行为：仍是无槽位范围的历史/通用补正事件，不得反推为两槽都已被具体要求，也不得删除或伪造旧记录。新 UI 的槽位选择只能作为显式新字段，不改变旧字段语义。

### 企业提交与专员核对

- 企业只可通过现有 `ADD_EVIDENCE` 在指定槽追加新版本；内容、来源标签和真实性状态仍按原资料合同处理。单纯新增/更换材料不得自动把补正标成已解决、`REVIEWED` 或 `LOCAL_CONFIRMED`。
- 提交新版本后，状态应明确表示等待原获派专员人工核对。只有专员在当前授权、当前 preparation revision 下成功执行 `REVIEW`，且被要求槽位的当前材料版本/hash 已不同于请求的 base（缺失base则现在有材料），才可在同一数据库事务中记录该请求针对的确切新版本/hash已人工核对并解决。当前双槽材料必需存在的原规则仍保持。
- 一次 `REVIEW` 可为当前快照中已提交新版的槽记录精确核对结果；未变化的其他槽请求仍保持打开，不得因整体审核或某槽补齐而静默解决。只要仍有显式补正请求未解决，资料整体就不能变成可企业 `CONFIRM` 的 `REVIEWED`；可展示已核对槽与仍待更新槽，但保持 `CHANGES_REQUESTED`/等效阻塞状态，并继续要求后续版本和人工核对。
- 请求之后若当前来源再次变化，旧resolution仍是历史事实，但不能称为当前有效核对。读取和后续写入口必须将当前 source version/hash 与被解决时的 version/hash 比较；发现新变化就显示需重验，并继续执行现有 `review_sha256`/来源门禁。不能让曾经解决的请求状态覆盖较新的材料变化。
- `REVIEW` 与 resolution 事件应在一个事务中写入；任何校验失败、CAS冲突或事务回滚都不能只留下“已解决”记录。actor/key 同参数重放恢复相同结果；不同参数或不同 Case scope 冲突。授权检查必须先于历史键回放。
- 原 `CONFIRM` 仍仅由企业执行，且要求 `review_sha256` 等于当前快照、没有未解决的显式补正请求；补正请求、ADD_EVIDENCE 或失效观察后旧确认不能继续生效。`REOPEN` 的既有历史和语义保持独立。

## 迁移、隐私和兼容边界

若实现需新增 `preparations` 上 JSONB 资料补正元数据，migration023 应只作 additive column/check；应用复用既有表 UPDATE 权限和 `preparation_events` INSERT 权限，不修改 `roles.sql`、身份、Grant、Run assignment、catalog writer 或 Case owner。迁移只在隔离测试库验证，不声称生产部署。

查询只向 Case owner 与当前获派 reviewer 返回其已授权范围；执行者不应通过新增补正API读到企业材料正文、诉求私有JSON或 reviewer 私有说明。通用 preparation response 仍移除私有 JSON 列，不能借 `REQUEST_CHANGES` payload 泄漏私有目标。不得复制其他企业的材料或授权作为模板输入。

JSON历史由应用逻辑保留，不应描述为数据库不可变/append-only，除非另有数据库约束支持。旧资料事件、既有 review/confirm 历史不回填成新的槽位请求或resolution；旧数据无法确知请求槽位时保持未知。

## 最小验证矩阵

1. 单槽补正：请求一个槽→企业只更新该槽→仍等待人工核对→专员核对当前版本→请求精确解决→企业可按当前哈希确认。
2. 双槽并行：请求两槽→只更新/只核对其一→另一请求仍打开并可见，整体仍不能企业确认；完成另一槽新版本和人工核对后才可进入整体当前审核/确认路径。
3. 同槽重开：同槽未解决时再次请求，旧 request 被保留并标 superseded，新 request 绑定当时最新 base；另一槽未解决请求不变。
4. 旧API兼容：不带槽位的旧 `REQUEST_CHANGES` 仍可走既有合同，不伪造槽位；旧 review/confirm/history 保留。
5. 当前来源失效：解决后同槽出现新版本或当前快照改变，旧 resolution 留在历史但当前投影需重验；不得继续 `CONFIRM` 或把旧hash报告为当前。
6. 角色/租户隔离：owner可补材料但不可审核；当前 assigned reviewer 可请求补正/核对；未分派/跨企业/撤权主体拒绝；执行者无新增材料详情。读/拒绝路径无业务写副作用。
7. 并发/幂等/失败：同 preparation revision 的并发补件或 Review 只能按CAS形成一个当前版本；同 key 同请求返回既有事件，不重复解决/生成版本；错误源、过期revision、DB失败均回滚槽位、状态和事件。
8. 回归既有 ENG096 同Case P1–P4 路径：资料补正后旧P1与下游验证失效，必须重新走原资料确认及计划核验；资源、接单、回执历史与权限记录不被覆盖或自动重放。

本切片不验收模板跨企业复用、正式规则/服务发布、Run访问自动配置、模型编排、P5真实业务关闭、AT08/AT35、真实履约、PR0-alpha 或完整 Windows/Win11。跨企业参数化模板仍是高优先级原V1目标（F2-T06/AT08、AT35），但需先确定正式 ServiceRelease 发布主体、来源版本协议及新Run合法访问边界；权限合同未确定时仅可做隔离Mock，不计作产品冷启动通过。
