# Compatible candidate Release to fresh independent Case: scope review

Read-only source review. No shared source/tests/docs/Git mutation and no PostgreSQL execution. New outputs are confined to .runtime/release-new-review; every older primary/audit root stays sealed.

## Plan support and smallest reusable boundary

Master §7.5 separates immutable service/template Releases from independent Case/reservation/receipt data, requires compatibility checks before upgrades, rejects destructive first-version migration, and forbids treating definition rollback as effect rollback. The preceding independent-new-input feature did not upgrade a service definition. This new slice can establish one compatible new reviewed candidate Release used by an entirely fresh Case, while retaining previous Case/history/resource effects. It must not claim same-Case migration, production publication, deployment or revival.

Reuse existing TemplateEngine author draft -> independent reviewer -> independent publisher command; existing TemplateDraft exact registered schema/goal closure validation; existing immutable source/release/event repository; existing catalog.register_release and bind_instance; existing cold original-five-command fresh input and explicit selection/adoption; original approval/resource/acceptance/receipt/verification. No clone/migration/revival API, general service-registration framework, additional database table or replacement compatibility journal is needed.

Smallest publish gate: an explicitly opted-in isolated TemplateEngine instance checks a pure finite compatibility result against its current REVIEWED draft and immutable previous same-scope Release, inside the original repository BEGIN IMMEDIATE transaction immediately before original publish INSERTs. The existing command accepts a strict explicit confirmation and expected preflight digest in strict mode; immutable publish event/payload binds the exact proof. The original engine command itself must check the mode, so direct Python callers cannot bypass an HTTP-only check. Keep legacy engine defaults unchanged. If an app opts in, require that it uses that exact opted-in engine rather than trusting a request-supplied flag.

## Existing preflight is not publication authority

ServiceReleasePreflight is specifically an owned-fixture observation for a single already adopted Case and two already registered published Release/instance pairs. Its contract states read_only, no publication/migration/adoption/execution/grants, and PG/source/journal are not a distributed commit. It folds current Case evidence, locks and dependency impact into classification. Do not turn can_record, an existing recorded snapshot, an old Case lock or its COMPATIBLE label into publisher permission. This would add circular dependencies, a larger cross-database race and a wrong authority boundary.

Reuse its finite comparison ideas where helpful, but the publication layer needs only a small pure definition comparison with existing TemplateDraft and frozen registered profiles. For the first bounded demonstration, allow informational name/description and a newly independently reviewed current source revision while preserving service_id/version, fixed parameter_schema, all six existing required goals and exact registered adapter/dependency contract. Reject removed goals, executable contract/parameter changes, unsupported profile/family, malformed history or unverifiable baseline. Do not equate compatible-for-fresh-input publication with automatic validity for existing Case evidence. Existing old Cases need their own original change contract if continued.

## Critical compatibility and history pitfalls

1. Original RETURN_DRAFT already sets the old PUBLISHED Release to SUPERSEDED and clears current_release. SAVE_DRAFT of a higher source revision makes the old source noncurrent. A strict publish preflight cannot use only draft.current_release or require the baseline Release still be currently available; it must query the complete bounded same-scope immutable prior Release history and validate its payload hash, original source binding, publication proof and forward content_version. A withdrawn or unknown source must not silently become current because a new draft exists; state/family rules must be explicit and fail closed.
2. Adding a default field directly to TemplateConfig changes existing model_dump bytes, durable template_contract fingerprints and old Release contract hashes. Adding optional Command fields changes original request fingerprints if serialized as None. Preserve legacy bytes explicitly: omit only the newly introduced absent compatibility fields from canonical command requests, not all historical None fields; conditionally append strict proof fields only in the strict path. Original strict models must reject compatibility fields on unrelated actions.
3. Preflight digest must bind current scope, draft revision/content_version/hash, review identity/revision/hash, immutable baseline Release id/payload hash/state/version, current source identity/version/hash/head, authority contract and registered profile. It must not include an ever-changing evaluation clock or a future random Release UUID. Recompute under original publication write transaction and revalidate present-time expiry/authority before writing. Confirming a stale preview or a boolean-like 1 must fail.
4. Do not rely on an app checkbox or a previously saved Case preflight for authority. Original independent author/reviewer/publisher permissions remain dynamic. Same key/identical complete strict request must preserve original committed result semantics; changed expected proof/confirmation/reason/validity must conflict. Current revocation must remain denial, and cold recovery cannot replay POST or turn historical publication into available authority.
5. The opted-in gate is scoped to that original isolated engine contract. If legacy engines can reopen the same repository without the strict policy, do not claim a global repository-wide prohibition unless the mode is separately durably bound. A process-only switch is not a persistent security boundary. Avoid silently updating old contract schemas to manufacture that claim.

## Transactions and lock-order limits

TemplateRepository.transaction already uses SQLite BEGIN IMMEDIATE and original command serializes with self.lock, then checks the durable contract head inside the transaction. A pure draft compatibility check belongs there. Do not invoke PG/catalog resolution from inside publication gate: original catalog operations already own PG locks before some source reads, and adding reverse SQLite -> PG nesting can deadlock. Catalog registration and instance mapping remain later independently explicit owner-fixture operations; no distributed atomic publish-plus-PG rollout is implied.

Catalog._derive_release already derives a distinct capability Release id from template Release id and uses forward template content_version as revision. register_release verifies the exact current immutable reviewed source, and bind_instance enforces config revision. New cold inputs bind exact configuration and Release fingerprints and then original commands; no old Case inputs/approval/grants/resources are copied.

## Minimum useful verification scope

- Actual SQLite engine/API/UI: explicit new opt-in only; old default command bytes/replay and first publication remain compatible. First reviewed baseline -> independent reviewed compatible new draft -> preview -> checkbox -> original publish. Prove missing/false/numeric confirmation, stale definition/review/source/head/profile/baseline, rollback/nonforward and broken goal/parameter/profile/family history refuse with no Release/event writes.
- Real separate SQLite connections/engine instances: source or definition/authority change between preview and publish, both serialization orders, same key conflicts, commit-failure rollback and lost response followed by original read recovery. No fake process lock as sole race proof.
- Existing cold enabled owned PG app: separately register/map the new compatible published Release, then fresh user input and explicit adoption. Assert new template/capability/config bindings, distinct Case/plan/material/approval/receipt IDs, original six goals and five nodes, unchanged old Case records and occupied resources until independently authorized release. Historical old Release never revives; expired/withdrawn/UNKNOWN new source or disabled consumer refuses.
- Actual isolated HTML candidate publish confirmation and existing business HTML new input/adoption; use an offline planner only and disclose worker/assignment/approval bridge fixtures. Full business completion may be separate API evidence, not claimed as all-browser or real-model acceptance.

No broad older-module queue is justified before the direct modules are complete. Keep current historical remaining baseline 96 modules/2400 nodes separate from any new batch totals and update only for fully executed intersections. Native Windows, formal AT, real models, production deployment, cross-process recovery and same-Case accepted in-flight migration remain gaps unless independently executed within explicit scope.
