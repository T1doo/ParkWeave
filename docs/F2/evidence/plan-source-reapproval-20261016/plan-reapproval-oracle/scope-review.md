# Independent scope and literal design review

Baseline `a794a1802e15100d691a969f0813aa371d707c36`. Read original V1 §7.4/8 and F2-T03/T05, `service_plan_approval`, `case_resource_delivery`, `case_resources`, and `resource_plan_binding`. No tests or source edits performed.

The smallest useful slice is explicit reapproval of a fresh replacement resource delivery for one existing synthetic Case. It is not a generic governance engine. Original first-delivery default refuses existing link history and must retain that behavior. Reapproval must be explicit in the request contract; no implicit fallback from original delivery.

Current Approval already binds exact original delivery command, preparation/current P1 sources, plan revision/definition, actor and Run state/fence, authority and resource revisions, and original hold-validity deadline. Current resource COMMIT then original binder and Approval CONSUME are one transaction. Reuse these primitives and their final commit checks. Add exact latest existing resource association identity/revision/snapshot or receipt evidence because first-delivery previously assumed an empty link history.

After source change, original owner must explicitly ADOPT local revision. Correct materials/fact-purpose prerequisites through original APIs and explicitly VERIFY P1. Then capture a new exact plan revision and new HELD members. Owner explicitly PROPOSES and APPROVES the fresh command, COMMIT confirms the new combination and appends one original Case binding at latest revision+1, and the same transaction consumes the new Approval. Every lock wait is followed by current database-clock, source, authority and validity recheck. P2–P5 remain unverified until their separate original repairs and VERIFY calls.

Old source receipts, Approval events, Case links, goals, step UUIDs, note bytes, unaffected locks and original plan journal prefix remain immutable. Superseding a Case association never releases or cancels the old confirmed combination. New capacity calculations must still include old occupancy. New replacement intent uses a fresh key and Approval object; old consumed Approval cannot be replayed as a new effect. Exact same successful key recovers its own historical receipt, including after original consent or hold TTL expires, and reports present source status separately.

A reapproval snapshot is exact, not a promise of future validity. Plan revision changing after APPROVE invalidates it even if definition hash remains unchanged. New resource/link/catalog/Run/authority versions invalidate it; revoke and restore cannot revive a snapshot. COMMIT late expiry, claim or receipt insertion failure rolls back holds confirmation, group, receipt, claim, link and consumption atomically. Unknown original-key GET returns NOT_OBSERVED and performs no write or inferred success. Denied recovery never bypasses current scope or exposes private receipts.

Keep the currently documented uncoordinated administrator boundary: do not add permissions to lock or update rows otherwise SELECT-only. Cooperative catalog proof already has an explicit opt-in protocol; use only an exactly matched installed protocol or refuse. A synthetic fixture proving local source epoch mismatch is not production governance, an external resource commitment or a formal approval authority.

Literal design has 32 rows. Symbol names are fixed intent references; actual IDs, versions, digests and UTC intervals must be recorded by eventual test fixtures, not filled from current rows to repair missing history. Distinguish full six-goal HTTP/PG evidence, shipped HTML with Node DOM, pure history mutations, and old-protocol compatibility. Windows, real browser, formal AT, real models and production remain NOT_RUN.

RA12 is intentionally unresolved: the app's existing link history is insert-only, so a latest-link ABA cannot be fabricated by rewriting historical rows or disabling the immutable trigger. An actual concurrent latest-link revision change is valid coverage but must be classified as a variant, or RA12 stays NOT_RUN.
