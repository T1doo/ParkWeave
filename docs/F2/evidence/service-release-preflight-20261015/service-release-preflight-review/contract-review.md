## Relevant actual boundaries

- `service_capability_contract.py` current `validate_release` uses current registry/actions plus current validity, while `validate_release_integrity(...saved registry/actions, accepted_at)` proves historical admission without current authority. `service_selection_candidates._proof` and `consumption_proof` authenticate V4 saved catalog/profile/selection/adoption. Do not substitute current compiler for a saved historical profile or substitute historical integrity for new target admission.
- `IsolatedServiceCapabilityCatalog` requires explicit original owned fixture and exact allowlist. Its `_current_release` resolves original reviewed immutable source, source head, dynamic author/reviewer/publisher scopes, contract/registry and time; `snapshot` uses actual current mapped objects/permissions. `_current_release` does **not** itself require `template_drafts.current_release == target` and same finite service kind does **not** establish same template family.
- `TemplateUpgrade._check` is an existing template-instance check/choice/migration family. New ServiceRelease/V4 preview must not reuse a generic template consumer record as evidence that the Case selected a logical capability release, or reuse its broad any-lock-and-needs rule when claiming an exact unaffected partition.
- Original `ConsumerRepository` has strict exact four tables and immutable binding/request/stage-body triggers. A distinct dedicated standard-schema file can journal preflight evidence without adding PG tables or changing original consumers. Do not insert new preflight stages in the original consumer's journal: `_stages` and unresolved-stage rules consume those rows as business sequencing.
- PostgreSQL current snapshots are not one atomic transaction with SQLite receipt persistence. Source template writer leases and PG advisory/principal/resource locks have an established order; read-only preflight must not invert it by waiting on a template writer while holding PG locks.

## Required contract decisions and refusal boundaries

1. Identify the original selected V4 capability ref exactly (release ID/revision/hash + instance ID/config revision/hash), original Case/preparation/Run/owner and current plan UUID/revision/hash. Verify historical consumption/profile plus all original event proofs. Legacy/partial/unproven plans are explicitly unsupported/UNKNOWN; never reinterpret as a different compiler.
2. Target is an explicit trusted current **same-family** logical service release/configuration. Family must include service kind plus original owner organization and template scope/template ID; unrelated templates with the same service ID/revision numbers are not upgrades. Require exact target hash/config and current owner/park/roles/resources/field mapping. State whether target must be current template head or merely an exact currently available reviewed revision; a function named `_current_release` does not prove newest head.
3. Original Release history remains immutable/readable after supersession/expiry; whether current preflight may compare from retired old source must be explicit. Recommended: authenticate original historical proof, list prior_current_available independently, require fresh target availability, and conservatively report current Case invalidity. Requiring the old source to be latest/current can reject every ordinary source-version upgrade. Old history never grants target permission. Target withdrawal/expiry/source UNKNOWN, changed registry, missing current authority or ambiguous lineage cannot yield COMPATIBLE/permission to act.
4. Distinguish `contract_delta` from existing `current_case_recheck` and any unknown scope; compute the conservative final union. An unrelated catalog-set addition can stale the original whole V4 binding and must not be mislabeled a target-specific semantic change. A metadata-compatible target never hides a current capacity/material/receipt defect.
5. Stable original step UUIDs and P1–P5 dependencies are references in a read result only. Source/contract differences may require recheck, but preflight changes no original event, source fingerprint, plan revision, current invalidation flag, manual allocation/lock, goal evidence, lifecycle, resources/reservations/receipts or other Case. Locked affected steps report LOCK_CONFLICT; unaffected locks remain preserved. No automatic UNLOCK/VERIFY/ADOPT or UI-generated original POST.
6. GET directory/preview/receipt recovery writes no journal and no PG business table. Only explicit save-evidence POST may append an immutable evidence record to the **separate** journal. Save payload contains expected server-preview digest and bounded selectors/reason, never client affected/proof/authority. Under original auth/current locks, recompute and compare the full current basis immediately before journaling.
7. Evidence receipt content is historical. After lost receipt/restart, GET returns original exact bytes and separately recomputed current_available/current classification; denied caller is refused before lookup/content. Expired/withdrawn/UNKNOWN targets or changed plan/auth cannot resurrect a current COMPATIBLE result through a cached saved result. Same actor/key with any changed parameter conflicts; no automatic resave/replay on GET.
8. Every saved basis binds projection/compiler version, plan ID/revision/source proof, target and original exact release/config identity, current source/catalog/auth/resource epochs and Case/Run/preparation xmin. A→B→A changes in values must be refused by epochs; source/review validity must be rechecked after waits, not just at request entry. Explicitly limit post-final-read trusted administrator races rather than claim a cross-store atomic guarantee.
9. Bound catalog discovery, journal records, request key/reason, manifest bytes and numeric revisions with strict scalar types (bool is not integer). Unknown/deep/duplicate-key/tampered proof shapes fail closed. Busy journal/PG locks use existing bounded409 behavior, no indefinite wait or retry with new key. Overflow does not silently drop records or imply all checked.
10. UI isolates owner/token/Case/plan/target/config/source epoch/generation; current403 clears private output, late/ABA responses cannot clear or overwrite a newer view. Separate “save preflight evidence” from old business action buttons. Stored preflight proof must not become an adoption candidate or Approval.
