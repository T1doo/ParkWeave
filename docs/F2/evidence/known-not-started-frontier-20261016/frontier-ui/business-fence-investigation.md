- Dispatch GET `/api/preparations/{id}/dispatch` and specialist GET `/api/service-dispatches/catalog?preparation_id=...` are read sequentially by `loadDispatch` (962). Both captured business_frontier values must match, in addition to the existing preparation/dispatch revision comparison. `renderDispatch` (940) captures a copied frozen fence in dispatchContext. `dispatchWrite` (988) appends the captured fence to OFFER or ordinary dispatch commands before original idempotency signature generation. It must never fetch a replacement fence while submitting or silently update dispatchPending.body during retry.
- Receipt CREATE uses a separate catalog read in receipt-prepare (1035); receiptCreateContext captures that exact fence, and receipt-create (1036) appends it without another read. Existing preparation identity/generation and revision guards remain.
- Receipt GET `/api/executor-receipts/{id}` flows through `loadReceipt` (1028) and `renderReceipt` (1027); receiptContext captures the fence. `receiptCommand` (1031) appends the captured fence before original signature generation. The existing local-adapter execute-local path (1030) is a separate writer and requires explicit backend decision: guarded with fence or refused for protocol-born preparations.
- Lifecycle GET and renderLocalCase (1115) capture the fence in localCaseContext. localCaseCommand (1159) appends it before opaque handle registration and original POST. Recovery uses existing exact-key GET; no new POST or auto-CAS repair.
- Dispatch handoff/sendHandoff is another independent writer. The backend must explicitly fence or refuse it for protocol-born preparations; UI must not assume the main OFFER DTO covers it.

Shared helper design: validate exactly the backend's five fence keys/types/bounds, clone/freeze at read/render time, attach expected_business_frontier only when the observed context has a valid fence. A present malformed/null fence is refused. An entirely absent field preserves ordinary nonprotocol DTO bytes. Do not synthesize generation/plan/epoch or infer protocol participation from UI status. Context generation/token/preparation/id guards remain as before; service-plan navigation additionally checks a present fence against the source plan identity/revision when exact source context is available.

Tests: actual shipped handlers with controlled GET data must prove captured epoch remains unchanged in POST even if a newer global view becomes available; stale plan/epoch rejection is handled by actual backend CAS, never replaced by a client refresh.
